## Note Manager

| Событие | Название | Категория |
| :------ | ---- | ---- |
| StudentCTF 2026 | Note Manager | pwn |

### Описание

>!!! Libc 2.35 !!!
>
>Сервис по управлению записочками, в котором писать можно не только в записочки

### Решение

Таск представляет собой сервис по управлению записками. Внимание игрока сразу должно привлечь Дебаг меню. Войти в него можно только зная пароль, который зависит от времени подключения пользователя. Время подключения выводится на экран при подключении поэтому не составляет сложности для игрока генерировать пароль самому. Получение доступа к Дебаг меню позволяет вычислить адрес бинаря (pie leak).

Основная уязвимость заключается в использовании указателя notes[idx]->data после освобождения соответствующей области в куче. Функция delete_note() вызывает free(), но не зануляет указатель. Из-за этого show_note() дает возможность читать освобождённую память, а edit_note() записывать в неё. Это даёт игроку примитивы read-after-free и write-after-free, которые используются для утечки адресов кучи и libc и последующего tcache poisoning.

В итоге выстраивается следующая цепочка эксплуатации уязвимости:

1) Получение времени подключения и восстановление пароля

2) Получение PIE leak через функцию Profile

3) Вычисление адреса базы бинаря

4) Создание большого heap chunk

    Игрок создает заметку размером 0x500, которая не помещается в tcache и после освобождения попадает в unsorted bin.

5) Эксплуатация UAF для получения libc leak

    После удаления заметки указатель notes[idx]->data остаётся валидным. Через show_note() можно прочитать уже освобождённую память. В начале unsorted-bin чанк находятся указатели fd/bk, связанные с main_arena внутри libc.

6) Вычисление базы libc

    По утёкшему адресу fd и известному offset main_arena вычисляется база libc. После этого становится известен адрес system().

7) Создание tcache chunks

    Создаются две заметки одинакового размера 0xf0, соответствующие одной tcache bin. После их удаления tcache содержит цепочку из двух чанков.

8) Получение heap leak

    Используется тот же UAF: указатель удалённой заметки продолжает указывать на freed chunk. Чтение этого чанка позволяет определить его адрес в куче.

9) Обход Safe-Linking

    Поскольку glibc 2.35 кодирует указатель next в tcache, эксплойт использует известный адрес освобожденного чанка и вычисляет корректное закодированное значение для нужного адреса.

10) Tcache poisoning через UAF write

    Через edit_note() производится запись в уже освобождённый чанк. Таким образом изменяется next элемент tcache и вместо следующего настоящего чанка указывается адрес globals.

11) Получение произвольного адреса через malloc()

    Первый malloc(0xf0) забирает отравленный чанк, после чего следующий malloc(0xf0) возвращает указатель на globals. Таким образом появляется примитив записи по произвольному адресу.

12) Перезапись globals.profile

    В начало globals записывается адрес расположенного рядом fake-буфера. Теперь globals.profile указывает не на настоящий Profile, а на контролируемую игроком область памяти.

13) Создание fake Profile

    В globals.fake формируется поддельная структура Profile: в command записывается /bin/sh, а в поле action — ранее найденный адрес system().

14) Перенаправление вызова

    При вызове show_profile() программа выполняет:
    ```
    profile->action(profile->command);
    ```
    Но profile уже указывает на fake Profile, поэтому фактически выполняется system("/bin/sh");
