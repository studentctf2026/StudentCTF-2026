## Мои расходы

| Событие | Название | Категория |
| :------ | ---- | ---- |
| StudentCTF 2026 | Мои расходы | web |

  
### Описание


> Я наконец-то свёл личные траты в одном месте. Особенно удобно сохранять разные фильтры — сервис сам заново собирает операции, когда я открываю нужный фильтр. Но старый мобильный клиент ведёт себя немного странно. Помогите найти флаг.


### Решение

В интерфейсе можно создать фильтр с периодом и вариантом сортировки. На странице справки сказано, что фильтры совместимы со старым мобильным приложением и старым API, а часть параметров сортировки этого приложения недоступна в веб-интерфейсе. Это повод посмотреть запрос при сохранении фильтра в DevTools или proxy.

В `POST /api/reports` отправляется JSON с полем `sortClause`:

```json
{
  "title": "Проверка",
  "periodStart": "2025-01-01",
  "periodEnd": "2026-01-01",
  "sortClause": "spent_at DESC, id DESC"
}
```

Веб-интерфейс предлагает только несколько значений, но сервер принимает любую строку подходящей длины. Сначала проверим, что это действительно влияет на отображение. Заменим значение на `id ASC`, сохраним фильтр и откроем предпросмотр. Первой операцией становится «Кофейня „Север“»: у неё минимальный ID `101`.

Обратный порядок можно получить выражением `-id ASC`: самым маленьким числом будет `-900`, поэтому первой отображается «Аренда квартиры». Так как `ORDER BY` допускает SQL-выражения, из этих двух сортировок удобно собрать булев oracle:

```sql
CASE WHEN 1=1 THEN id ELSE -id END ASC
```

При истинном условии первой будет кофейня, при ложном — аренда:

```sql
CASE WHEN 1=0 THEN id ELSE -id END ASC
```

Значение не выполняется при `POST` или `PATCH`: оно сохраняется параметризованным запросом. SQL строится только после отдельного `GET /api/reports/:id/preview`, когда сервер подставляет сохранённую строку в `ORDER BY`. Это second-order SQL injection. Ответ содержит лишь две обычные операции, поэтому результат условия наблюдаем только по их порядку.

Дальше проверяем PostgreSQL и при необходимости перечисляем таблицы через `information_schema`. В задаче секрет лежит в строке `name = 'flag'` таблицы `secrets`. Для одного бита флага используем:

```sql
CASE WHEN (
  SELECT ascii(substr(value, 1, 1))
  FROM secrets
  WHERE name = 'flag'
) > 77 THEN id ELSE -id END ASC
```

Если первой пришла «Кофейня „Север“», ASCII-код первого символа больше `77`; если «Аренда квартиры» — нет. Бинарным поиском по печатному ASCII (`32..126`) восстанавливаем символ, затем увеличиваем позицию `substr`. Останавливаемся на `}`.
