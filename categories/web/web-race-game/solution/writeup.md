## CAMPUS COURIER

| Событие | Название | Категория |
| :------ | ---- | ---- |
| Student CTF | Campus Courier | web |

### Описание

> Campus Courier — внутренняя университетская игра для курьеров. Нужно собрать три обычные посылки и забрать золотую посылку, которая находится за турникетом. Сервер обещает перемещать игрока не более чем на одну клетку за игровой такт.

### Решение

Сначала открываем игру и смотрим сетевой обмен в DevTools. `GET /api/session` создаёт cookie `cc_session` и возвращает стартовое состояние:

```json
{"player":{"x":1,"y":2,"lastSeq":0}}
```

Игровые команды идут не через HTTP, а через WebSocket `/ws`. Cookie браузер отправляет автоматически. Формат движения такой:

```json
{"type":"move","direction":"right","seq":1}
```

После успешного движения сервер рассылает всем WebSocket этой сессии сообщение `state`. Для сбора посылки используется команда:

```json
{"type":"collect","packageId":"package-1"}
```

Обычный маршрут до турникета можно пройти без уязвимости. Номера команд и координаты будут такими:

| `seq` | Команда | Координата после команды |
| :---: | --- | :---: |
| 1 | `up` | `(1,1)` |
| — | собрать `package-1` | `(1,1)` |
| 2 | `right` | `(2,1)` |
| 3 | `right` | `(3,1)` |
| — | собрать `package-2` | `(3,1)` |
| 4 | `down` | `(3,2)` |
| 5 | `down` | `(3,3)` |
| — | собрать `package-3` | `(3,3)` |
| 6 | `up` | `(3,2)` |

Если после этого обычным способом отправить `seq=7` с направлением `right`, игрок попадёт в `(4,2)`, а следующая команда `seq=8` из `(4,2)` в `(5,2)` получит ошибку `GATE_BLOCKED`. Значит, нужно найти отличие между проверкой команды и изменением состояния.

При анализе серверной логики видно следующее:

1. Обработчик читает `x`, `y`, `lastSeq` и `lastMoveAt` игрока.
2. Проверяет, что `seq` следующий, новая клетка находится на карте, а переход из `x=4` в `x=5` не выполняется.
3. После проверок ждёт фиксированные 250 мс.
4. После ожидания изменяет живое состояние относительным выражением `player.x += dx`.

Между проверкой и изменением состояния нет блокировки или повторной проверки. Поэтому открываем два WebSocket-соединения с той же cookie и почти одновременно отправляем в оба:

```json
{"type":"move","direction":"right","seq":7}
```

Оба обработчика успевают увидеть один и тот же снимок `(3,2)` и считают переход `(3,2) → (4,2)` допустимым. Через 250 мс первый обработчик делает `x: 3 → 4`, а второй — `x: 4 → 5`. Поле `lastSeq` в обоих случаях становится равным `7`, но координата увеличивается дважды. Игрок оказывается за турникетом.

После обхода остаётся выполнить два обычных шага:

```text
seq=8: right, (5,2) → (6,2)
seq=9: right, (6,2) → (7,2)
```

На клетке `(7,2)` отправляем:

```json
{"type":"collect","packageId":"golden-package"}
```

Сервер проверяет, что все три обычные посылки собраны, и отправляет WebSocket-сообщение `flag`. Значение флага не хранится во frontend — оно читается сервером из `flag.txt`.
