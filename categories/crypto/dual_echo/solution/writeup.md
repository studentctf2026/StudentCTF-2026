## Dual_echo
| Событие | Название | Категория |
| :------ | ---- | ---- |
| StudentCTF | Dual_echo| crypto |

  
### Описание


>Мы нашли странное казино, которое принимает ставки через публичный «маяк случайности». Организаторы утверждают, что генератор честный, но у нас есть подозрение, что это не так.

### Решение

В [params.json](params.json) указано `order == p`. Это первое, на что нужно
обратить внимание: порядок группы точек равен характеристике поля.
Такие кривые называются **аномальными** и печально известны тем, что
задача дискретного логарифма на них взламывается за линейное время
(Semaev 1998; Satoh–Araki 1998; Smart 1999). Ни один нормальный
генератор параметров такую кривую не выдаст — значит, она подобрана
намеренно.

Второй сигнал — в whitepaper. Провенанс точки `P` аккуратно
задокументирован (nothing-up-my-sleeve через SHA-256), а про `Q` сказано
лишь, что она «выбрана нашей командой». В настоящем Dual_EC именно
соотношение между `P` и `Q` содержит бэкдор: если `P = d·Q`, то знание
`d` ломает генератор. Здесь всё ровно так.

Атака Смарта: восстановление d

Пусть `E/F_p` аномальна, то есть `#E(F_p) = p`. Требуется решить
`P = d·Q`.

Идея SSSA — поднять задачу в кольцо `p`-адических чисел `Q_p` и
воспользоваться формальным логарифмом. Схема:

1. Поднять `E`, `P`, `Q` до `Q_p` (те же `a`, `b`; координаты точек
   поднимаем так, чтобы они лежали на кривой по модулю `p^k`).
2. Умножить обе точки на `p`. Точки `p·P̃` и `p·Q̃` попадают в ядро
   редукции `E_1(Q_p)` — «формальную группу» точек, близких к
   бесконечно удалённой.
3. Для точки ядра формальный параметр `t = -x/y` играет роль
   эллиптического логарифма (с точностью до `O(p^2)`). Логарифм линеен,
   поэтому

   ```
   t(p·P̃) = d · t(p·Q̃)   (mod p)
   ```

   откуда `d = t(p·P̃) / t(p·Q̃) mod p`.


```
d = 0xbd33c216b872c8923ba2298192a977e59c475faf73114ce660e54e7614a3eeb2
```

Проверка: `d·Q == P`.

Один шаг генератора:

```
s   <- x( s · P )
r   <- x( s · Q )
beacon <- младшие 240 бит r     (старшие 16 бит отброшены)
```

Пусть маяк соответствует внутренней точке `R = s·Q` (её мы не видим
целиком — известны лишь младшие 240 бит абсциссы). Тогда, зная `d`:

```
d · R = d · s · Q = s · (d·Q) = s · P
```

а `x(s·P)` — это ровно следующее состояние `s'`. То есть по точке `R`
бэкдор напрямую выдаёт следующее состояние генератора.

Проблема одна: `R` мы знаем не полностью — отброшены старшие 16 бит
абсциссы. Перебираем все `2^16` вариантов старших бит, достраиваем полную
абсциссу `r`, поднимаем на кривую (`lift_x`) и для каждого кандидата
проверяем гипотезу по следующему наблюдаемому маяку. Один правильный
кандидат — и состояние восстановлено.

Окно из 8 публичных маяков даёт с запасом материал и для восстановления,
и для перекрёстной проверки (кандидат должен воспроизвести все
последующие маяки окна, а не только один).


Восстановив состояние `s`, произведшее последний маяк окна, следующий
номер считаем детерминированно:

```
s'      <- x( s · P )
number  <- ( младшие 240 бит x(s'·Q) ) mod 37
```

Дальше — банальная жадность. Straight-up платит 35 : 1, значит каждый
верный номер умножает банк на 36. Ставим ва-банк на предсказанный
номер:

```
100 -> 3600 -> 129600 -> 4665600 -> 167961600 -> 6046617600
```

Пять верных ставок подряд — и банк перепрыгивает `10^9`. Казино отдаёт
флаг.
